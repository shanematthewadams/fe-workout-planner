## Atomic database read and cache

Local migration `supabase/migrations/20261026143249_exicon_read_snapshot.sql` was created through Supabase CLI and applied to the approved shared project as remote **`20261026145104 exicon_read_snapshot`**. Do not blindly push/reset/repair migration history; prior local/remote mappings are in the foundation handoff.

`public.fe_exicon_catalog()` returns one JSON snapshot assembled from the normalized tables. It is SQL/STABLE, SECURITY INVOKER, with an empty search path. It adds no write grants, ownership changes or row-policy exceptions. PUBLIC function execution is revoked and anonymous/authenticated/operator execution is explicit; all table RLS remains active. A single SQL statement avoids mixing parent/child states across multiple HTTP reads. Generated alias normalization is omitted from the version 1 payload; only sources linked to visible permissions are included. Revoked/draft parent chains disappear through existing RLS.

`server/exicon-intelligence.ts` reads that RPC using only the existing publishable key. Successful snapshots are cached for sixty seconds, concurrent reads coalesce, the cache is bounded to four connection identities, and payloads/row counts are bounded. Failure/malformed data is not cached as success. Application requests time out after two seconds and use the bundled guide; AO and Exicon reads run concurrently before generation. No workout request contacts the Nation API, and no AI call retrieves exercise facts.

The first operator-runtime read hit that short timeout. A diagnostic HTTP read returned valid JSON in 6.9 seconds while database EXPLAIN ANALYZE measured about 17 ms for the snapshot; the restricted operator network was the delay. `catalog:exicon-read` therefore uses an explicit fifteen-second diagnostic allowance and reports it. Application reads retain two seconds; staging endpoint/provider verification must prove that normal deployment path separately. The successful operator check made one RPC for two concurrent consumers and returned 8 published exercises, 15 aliases, 50 merged movements, zero blocked IDs and zero ambiguous aliases.

## Planner integration and safety

The adapter merges by stable canonical ID, retains all fifty fallback movements and preserves historical names/aliases for saved-plan constraint checks when a canonical record is renamed. Published database fields replace the corresponding eight app-written records; unrelated fallback records remain unchanged. This is a catalog migration, not a new exercise engine. The frontend offline template and existing saved-workout schema are preserved.

The same guide is passed into prompt eligibility AND output validation. Required equipment, running flags and facilities are enforced even when the AI omits `requiredFeatures` or gear/travel words. Unknown required amenity/equipment IDs block that exercise rather than falling back to weaker requirements. Today's closures still override profile/device knowledge. Unknown/multiple counting conventions explicitly require the Q to choose/demonstrate a full cycle. Ambiguous aliases are exposed as diagnostics and rejected in executed directions, never resolved by choosing the first row.

An exact canonical ID takes priority over aliases resembling that ID. Aliases never silently select a variation. The adapter can validate an explicitly selected variation's inherit/replace requirements; the present planner request contract exposes no variation selection and therefore uses canonical movements only. Regional aliases/counting apply to recognized FE AOs; custom/downrange input uses global conventions. Do not infer that a variation changes running classification from its name or instructions; extend explicit metadata before adding such a selection flow.

`GET /api/exicon?region=the-fe` returns the validated merged guide and source diagnostics, without credentials. It shares the same reader/adapter on Netlify and Vite and does not consume preview AI rate-limit slots. Production/deploy-preview reads remain hard-disabled by `exiconEnvironment`; branch deploys default to the approved shared catalog. `EXICON_CATALOG_ENABLED=false` is the branch kill switch. Connection settings reuse the existing AO catalog URL/publishable key. The generation response includes `X-F3-Exicon-Source` for technical verification. This diagnostic header is not a new claim that generated workouts are verified regional originals, and existing workouts are not rewritten when the catalog changes.
